# نقشه منابع مشترک Cloudflare برای SAHROUD

**هدف:** استفاده مشترک و قابل‌کنترل از امکانات Cloudflare در تمام نرم‌افزارهای فعلی و آینده، بدون ساخت Worker، D1، دامنه یا پنل تکراری و بدون انتقال ناخواسته داده‌های حساس به هسته مرکزی.

## ۱) لایه‌های معماری

| لایه | نام ثابت | مسئولیت | داده مجاز |
|---|---|---|---|
| Control Plane | Worker: `sahroud-central-api` | کاتالوگ، حساب، عضویت، طرح، اشتراک و مجوز | فراداده حساب و مجوز؛ نه داده عملیاتی |
| Control Plane DB | D1: `sahroud-central`, binding: `CORE_DB` | منبع یکتای اطلاعات مرکزی | هویت، حساب، عضویت، محصولات، اشتراک و مجوز |
| Telemetry مشترک | Worker: `sahroud-counter` | آمار رضایت‌محور همه محصولات | رویدادهای کم‌حساسیت و حداقل داده لازم |
| Telemetry DB | D1: `sahroud-counter`, binding: `DB` | ذخیره آمار مشترک محصولات | رویدادهای آماری؛ نه رمز، توکن یا GPS دقیق |
| داده حساس FAMILY GUARD | Worker: `sahroud-family-guard-api` | API کنترل والدین و موقعیت با رضایت صاحب دستگاه | موقعیت و مسیر؛ جدا از D1 مرکزی |
| داده FAMILY GUARD | D1: `sahroud-family-guard`, binding: `DB` | پایگاه مستقل اطلاعات مکانی | خانواده، دستگاه، دعوت و مختصات |
| پنل هر محصول | Pages: `sahroud-<product>-dashboard` | رابط وب محصول در صورت نیاز | فقط از API همان محصول/هسته استفاده کند |

نام‌های بالا قرارداد پروژه‌اند. وجود واقعی هر Worker یا D1 در حساب Cloudflare هنوز باید در خود حساب بررسی شود؛ نام فایل یا مستندات به‌تنهایی اثبات استقرار نیست.

## ۲) قواعد تخصیص منابع

- یک هسته مرکزی و یک D1 مرکزی برای تمام محصولات؛ برای هر کاربر، خانواده، پروژه یا دستگاه D1 نسازید.
- داده حساس یا پرحجم در D1 اختصاصی محصول بماند. داده مکان و مسیر FAMILY GUARD هرگز به D1 مرکزی منتقل نشود.
- برای محصولات کم‌حساسیت، فقط پس از طراحی و آزمون جداسازی چندمستاجری می‌توان از D1 اشتراکی رزروشده `sahroud-products-pool-01` استفاده کرد. این نام رزرو است و فعلاً نباید ساخته شود.
- در دیتابیس اشتراکی، همه queryها باید هم `product_key` و هم `account_id` را از هویت تأییدشده سمت Worker اعمال کنند. D1 خودکار Row-Level Security ندارد.
- آمار چند محصول در همان سرویس `sahroud-counter` می‌ماند؛ برای هر نرم‌افزار Worker یا D1 آمار جدا ساخته نشود.
- Worker قیمت METREH فقط در صورت نیاز به همان درگاه موجود متصل می‌ماند؛ Worker یا D1 دیگری برای قیمت‌ها بدون بررسی ساخته نشود.
- R2 برای فایل‌ها و خروجی‌های حجیم؛ KV فقط برای cache و تنظیمات کم‌تغییر؛ هیچ‌کدام منبع اصلی مجوز یا نشست نیستند.
- Queues و Durable Objects فقط وقتی ایجاد می‌شوند که نیاز واقعی و آزمون بار آن را ثابت کند.
- آدرس‌های فعلی GitHub Pages و لینک‌های عمومی محصولات حفظ می‌شوند. استفاده از Worker به معنی انتقال اجباری سایت‌ها به Pages نیست.

## ۳) قرارداد نام‌گذاری برای محصولات بعدی

| نوع منبع | الگوی نام |
|---|---|
| Worker محصول | `sahroud-<product>-api` |
| D1 اختصاصی محصول | `sahroud-<product>` |
| Pages محصول | `sahroud-<product>-dashboard` |
| فایل R2 | `<product>/<account_id>/<object_id>` |
| binding پایگاه مرکزی | `CORE_DB` |
| binding دیتابیس عملیاتی محصول | `DB` |
| CORS هسته مرکزی | `CORS_ALLOWED_ORIGINS` |

استثناهای موجود که برای جلوگیری از شکستن نسخه‌های مستقر باید فعلاً حفظ شوند:
- Worker و D1 آماری فعلی از نام‌های `sahroud-counter` و binding برابر `DB` استفاده می‌کنند.
- Worker قیمت METREH از متغیر `ALLOWED_ORIGIN` استفاده می‌کند. فقط هنگام مهاجرت کنترل‌شده به قرارداد جدید تغییر داده شود.
- Family Guard از D1 اختصاصی و binding برابر `DB` استفاده می‌کند.

## ۴) سقف‌های مهم طرح رایگان — بررسی در ۲۲ نوامبر ۲۰۲۶

| سرویس | سقف رایگان مهم | نتیجه برای معماری |
|---|---|---|
| Workers | ۱۰۰٬۰۰۰ درخواست در روز، ۱۰ میلی‌ثانیه CPU برای هر درخواست، ۱۲۸ مگابایت حافظه؛ حداکثر ۱۰۰ Worker در حساب | درخواست‌ها باید سبک، cache و تعداد Workerها مدیریت شوند |
| D1 | ۱۰ دیتابیس در هر حساب، ۵۰۰ مگابایت برای هر دیتابیس، مجموعاً ۵ گیگابایت، ۵ میلیون ردیف خوانده‌شده در روز، ۱۰۰ هزار ردیف نوشته‌شده در روز، ۷ روز Time Travel و حداکثر ۵۰ query subrequest در هر اجرای Worker | قبل از ساخت D1، موجودی کل حساب بررسی شود؛ از ساخت دیتابیس‌های ریز و تکراری و نوشتن بیش از حد موقعیت جلوگیری شود |
| R2 Standard | ۱۰ گیگابایت-ماه ذخیره‌سازی، یک میلیون عملیات Class A و ده میلیون عملیات Class B در ماه؛ خروجی اینترنت رایگان؛ سهمیه رایگان فقط برای کلاس Standard است | برای فایل‌ها مناسب است، اما فعال‌سازی R2 نیازمند فعال‌کردن اشتراک R2 و تکمیل مرحله checkout در داشبورد Cloudflare است |
| Workers Builds | تنظیم Root directory، Build command و Deploy command برای هر Worker | در monorepo هر Worker فقط مسیر خودش را build/deploy کند |

**نکته فعال‌سازی R2:** وجود سهمیه رایگان ماهانه به معنی فعال بودن خودکار سرویس در حساب نیست. پیش از ساخت bucket باید اشتراک R2 در داشبورد فعال و مرحله checkout تکمیل شود. تا زمانی که واقعاً به ذخیره فایل حجیم نیاز نداریم، R2 را فعال یا bucket جدید ایجاد نمی‌کنیم.

سقف‌ها ممکن است تغییر کنند؛ پیش از هر توسعه یا افزایش مصرف، صفحات رسمی زیر دوباره بررسی شوند. طرح رایگان ظرفیت نامحدود یا تضمین ظرفیت ۱۰۰ هزار کاربر نیست.

## ۵) مواردی که اکنون نباید ایجاد شوند

- D1 جدید برای هر محصول صرفاً به دلیل وجود محصول.
- دیتابیس جداگانه برای هر حساب، خانواده، دستگاه یا پروژه.
- D1 رزروشده `sahroud-products-pool-01` پیش از طراحی و آزمون جداسازی داده.
- KV، R2، Queue یا Durable Object بدون مصرف واقعی.
- دامنه یا Worker تکراری برای سرویس‌هایی که نام قراردادی دارند.
- API احراز هویت، اشتراک یا پرداخت با پاسخ ساختگی، کلید ثابت داخل APK/JavaScript یا دسترسی کلاینت مستقیم به D1.

## ۶) ترتیب اجرایی استاندارد

1. موجودی Workerها، D1ها، Pages، KV و R2 حساب بررسی و در یک فهرست ثبت شود.
2. فقط در صورت نبود منبع مرکزی و وجود سهمیه، `sahroud-central` ساخته شود.
3. migrationهای نسخه‌دار هسته مرکزی اجرا و API فقط‌خواندنی آزمایش شود.
4. احراز هویت، نقش‌ها، صدور مجوز، لغو دسترسی و ثبت audit سمت سرور طراحی و آزمون شود.
5. محصولات به‌ترتیب اولویت، با شناسه ثابت و قرارداد API به هسته متصل شوند.
6. داده عملیاتی هر محصول در جای مناسب خودش بماند و پس از آزمون حریم خصوصی و بار، انتشار تولیدی انجام شود.
