# SAHROUD CENTRAL

هسته زیرساخت مشترک محصولات SAHROUD روی Cloudflare. این پروژه لایه کنترل مرکزی است که محصولات فعلی و آینده از قرارداد مشترک آن استفاده می‌کنند؛ نه یک پنل رهگیری یا یک محصول منفرد.

## معماری مصوب

### لایه مرکزی (Control Plane)

- Worker ثابت: sahroud-central-api
- D1 ثابت: sahroud-central با binding برابر CORE_DB
- داده‌های مرکزی: هویت، حساب شخصی/سازمانی، عضویت، کاتالوگ محصولات، طرح‌ها، اشتراک‌ها، مجوزها و رویدادهای ممیزی
- API نسخه‌دار: همه مسیرهای عمومی زیر /v1/ قرار می‌گیرند.

### لایه محصولات (Product Data Plane)

کد و داده عملیاتی محصولات از لایه مرکزی جدا می‌مانند. اما جداسازی منطقی محصول الزاماً به معنی ساخت یک D1 فیزیکی برای تک‌تک محصولات نیست؛ تخصیص منبع با توجه به حساسیت داده، حجم، نیاز بازیابی و سهمیه حساب انجام می‌شود.

- داده‌های بسیار حساس یا پرحجم، مانند موقعیت و مسیر FAMILY GUARD، در D1 اختصاصی همان محصول می‌مانند.
- محصولات کم‌حساسیت می‌توانند از D1 اشتراکیِ محصولات استفاده کنند؛ به شرط آنکه تمام جداول و پرس‌وجوها به product_key و account_id محدود شوند و این مقادیر فقط از هویت احراز‌شده سمت سرور تعیین شوند.
- هیچ محصولی اجازه ندارد داده‌های محصول دیگر را بخواند یا بنویسد. D1 اشتراکی به معنی اشتراک دسترسی نیست.
- برای هر کاربر، خانواده، دستگاه یا پروژه D1 جداگانه نسازید.
- D1 مرکزی هرگز محل نگهداری مختصات، اطلاعات سلامت، فایل خصوصی یا محاسبات عملیاتی محصول نیست.

## سیاست تخصیص منابع Cloudflare

| منبع | نام / الگو | قاعده |
|---|---|---|
| Worker مرکزی | sahroud-central-api | API مشترک و کاتالوگ |
| D1 مرکزی | sahroud-central | فقط کنترل مرکزی |
| Worker محصول | sahroud-<product>-api | منطق محصول؛ با نام و نسخه مستقل |
| D1 اختصاصی | sahroud-<product> | برای داده حساس، پرحجم یا نیازمند جداسازی فیزیکی |
| D1 اشتراکی کم‌حساسیت | sahroud-products-pool-01 | فقط با جداسازی سخت‌گیرانه product_key و account_id در سرور |
| Pages | sahroud-<product>-dashboard | پنل وب محصول |
| R2 | پیشوند کلید /<product>/<account_id>/ | فایل‌های حجیم؛ دسترسی فقط از Worker |
| KV | cache / تنظیمات کم‌تغییر | منبع اصلی داده یا مجوز نیست |
| Queues / Durable Objects | بر اساس نیاز اثبات‌شده | در گام اول ایجاد نمی‌شوند |

نام sahroud-products-pool-01 یک قرارداد رزروشده است، نه دیتابیسی که اکنون باید ساخته شود. استفاده از آن فقط پس از بررسی سهمیه و طراحی schema چندمحصولی مجاز است.

منابع اختیاری مانند R2، KV، Queues و Durable Objects از ابتدا بی‌دلیل ساخته نمی‌شوند. ابتدا از امکانات موجود و طرح رایگان استفاده می‌کنیم و فقط با نیاز واقعی منبع جدید اضافه می‌شود.

## قرارداد API فعلی

- GET /health — سلامت Worker و اتصال D1 مرکزی
- GET /v1/version — نسخه API
- GET /v1/catalog/products — کاتالوگ زنده از D1 مرکزی
- GET /v1/catalog/products/{product_key} — اطلاعات عمومی یک محصول

API فعلی فقط خواندنی است. ورود کاربر، ایجاد حساب، صدور/ابطال کلید، فعال‌سازی اشتراک، پرداخت و اعتبارسنجی مجوز هنوز فعال نیستند. این محدودیت عمدی است تا ابتدا تأمین‌کننده هویت، سیاست نقش‌ها و روش امن مدیریت کلید تعیین شود. هیچ محصولی نباید تا آن زمان دسترسی تجاری را با پاسخ ساختگی یا کلید ثابت داخل برنامه فعال کند.

## توسعه محلی

نیازمند Node.js 20 یا بالاتر:

1. وارد پوشه platform شوید.
2. دستور npm install را اجرا کنید.
3. دستور npm test را اجرا کنید.
4. برای توسعه از npm run dev و D1 محلی Wrangler استفاده کنید.
5. برای آزمون اولیه نیازی به ساخت D1 راه‌دور جداگانه نیست.

## استقرار اولیه

1. ابتدا موجودی D1 حساب Cloudflare را ببینید.
2. اگر sahroud-central وجود ندارد، فقط در صورت وجود سهمیه آن را بسازید.
3. Database ID را در platform/wrangler.toml جایگزین placeholder کنید؛ API Token یا Secret را هرگز در Git قرار ندهید.
4. migration را با npm run db:migrate:remote اجرا کنید.
5. Worker را با نام sahroud-central-api و Root directory برابر /platform به GitHub متصل کنید.
6. Deploy command برابر npm run deploy باشد.
7. پس از انتشار، /health را بررسی کنید؛ مقدار dependencies.core_db باید ok باشد.

راهنمای کامل و مسیرهای پنل در CLOUDFLARE-SETUP.md است.

## سهمیه و پایداری

در طرح رایگان D1، سقف حساب ۱۰ دیتابیس، حداکثر اندازه هر دیتابیس ۵۰۰ مگابایت و سقف فضای کل حساب ۵ گیگابایت است. این سقف شامل دیتابیس‌های موجود حساب هم می‌شود. بنابراین قبل از ساخت هر D1 جدید، فهرست و تعداد دیتابیس‌های موجود بررسی شود.

توسعه و آزمون اولیه با D1 محلی Wrangler انجام می‌شود. در استقرار واقعی، D1 اختصاصی را فقط برای محصول حساس یا پرحجم بسازید و محصولات کم‌حساسیت را در صورت نیاز و با کنترل سخت product_key و account_id در یک دیتابیس اشتراکی قرار دهید. حتی در دیتابیس اشتراکی، مجوزها باید در سمت سرور اعمال شوند؛ D1 قابلیت Row-Level Security خودکار ندارد.

طرح رایگان برای شروع و آزمایش مناسب است، اما ظرفیت ۱۰۰ هزار کاربر بدون آزمون بار، پایش سهمیه، پشتیبان‌گیری، کنترل سوءاستفاده و بررسی هزینه تضمین نمی‌شود.
