# الگوی اتصال هر محصول SAHROUD

این سند قرارداد لازم برای افزودن محصولات موجود و آینده به زیرساخت مرکزی است.

## ۱. ثبت هویت محصول

هر محصول یک product_key ثابت و یکتا دارد. کلید پس از انتشار نباید تغییر کند.

| محصول | product_key | دسته |
|---|---|---|
| FAMILY GUARD | family-guard | safety |
| STEEL | steel | engineering |
| METREH | metreh | construction |
| UTM | utm | surveying |
| TASBIH | tasbih | utility |
| GAMES | games | games |

ثبت یا تغییر کاتالوگ از طریق migration جدید انجام می‌شود؛ فایل migration اجراشده را بازنویسی نکنید.

## ۲. انتخاب دیتابیس و نام‌گذاری منابع

برای هر محصول، ابتدا سطح حساسیت، حجم، نرخ نوشتن، نیاز بازیابی و سهمیه D1 حساب بررسی می‌شود.

- Worker محصول: sahroud-<product>-api
- Pages پنل: sahroud-<product>-dashboard
- D1 اختصاصی، در صورت نیاز: sahroud-<product>
- D1 اشتراکی کم‌حساسیت، در صورت نیاز: sahroud-products-pool-01
- R2 در صورت نیاز: کلیدها با پیشوند <product>/<account_id>/

قواعد تخصیص:

1. داده حساس یا پرحجم باید در D1 اختصاصی محصول بماند. نمونه روشن: موقعیت و تاریخچه مکان FAMILY GUARD.
2. محصولات کم‌حساسیت می‌توانند در D1 اشتراکی ذخیره شوند؛ در آن صورت تمام ردیف‌ها باید product_key و account_id داشته باشند و تمام خواندن/نوشتن‌ها در Worker با هر دو مقدار محدود شوند.
3. در D1 اشتراکی، هرگز شناسه مالک یا محصول را فقط از ورودی کلاینت معتبر ندانید؛ شناسه حساب را از نشست/توکن معتبر سمت سرور استخراج کنید.
4. برای هر کاربر، خانواده، دستگاه یا پروژه دیتابیس جدا نسازید.
5. D1 مرکزی sahroud-central فقط برای حساب/هویت/عضویت/کاتالوگ/اشتراک/مجوز است و محل داده عملیاتی هیچ محصولی نیست.
6. سقف رایگان D1 ده دیتابیس برای کل حساب است؛ موجودی حساب را پیش از ایجاد دیتابیس فیزیکی بررسی کنید. برای توسعه معمول از D1 محلی Wrangler استفاده کنید.

## ۳. مرزبندی داده‌ها و چندمستاجری

در D1 مرکزی فقط داده مشترک حساب/هویت/عضویت/محصول/اشتراک/مجوز نگهداری می‌شود. داده‌های مکان، سلامت، پروژه، نقشه، فایل خصوصی یا اطلاعات عملیاتی در دیتابیس اختصاصی محصول یا D1 اشتراکیِ محصولات کم‌حساسیت باقی می‌مانند؛ نه در D1 مرکزی.

برای داده چندمستاجری:

- تمام جداول عملیاتی باید مالکیت ردیف را به‌صورت روشن ثبت کنند.
- تمام queryها باید هم product_key و هم account_id را محدود کنند.
- این دو مقدار باید از هویت تأییدشده در Worker به دست آیند، نه از پارامتر قابل‌دستکاری کلاینت.
- هیچ مسیر مستقیمی از مرورگر یا APK به D1 داده نشود.
- آزمون‌های منفی برای تلاش دسترسی حساب یا محصول دیگر نوشته شود.
- اگر جداسازی فیزیکی لازم است، محصول D1 اختصاصی بگیرد.

D1 خودش row-level security خودکار ارائه نمی‌کند؛ جداسازی در دیتابیس اشتراکی باید در لایه Worker به‌طور کامل اجرا و آزمون شود.

## ۴. اتصال کلاینت به کاتالوگ مرکزی

آدرس API باید از تنظیمات محیطی برنامه دریافت شود؛ URL تولید را در چند فایل یا نسخه اپ کپی نکنید.

مسیرهای عمومی فعلی:
- GET /health
- GET /v1/version
- GET /v1/catalog/products
- GET /v1/catalog/products/{product_key}

نمونه درخواست:

    const response = await fetch(CENTRAL_API_BASE + "/v1/catalog/products");
    if (!response.ok) throw new Error("SAHROUD Central is unavailable");
    const catalog = await response.json();

این مسیرها فقط داده عمومی کاتالوگ را می‌دهند. احراز هویت، مدیریت حساب، صدور مجوز و اشتراک هنوز پیاده‌سازی نشده‌اند.

## ۵. Cloudflare Pages و Workers در monorepo

برای Worker:
- Repository: sahroud/danky
- Root directory: /platform یا پوشه اختصاصی همان Worker
- Build command: خالی، مگر آنکه build خاصی لازم باشد
- Deploy command: npm run deploy
- Worker name: دقیقاً برابر name در فایل wrangler.toml همان پوشه باشد
- فقط مسیرهای مرتبط همان Worker در Build watch paths قرار گیرند تا تغییر محصول دیگر باعث Deploy بی‌مورد نشود.

برای Pages:
- Repository: sahroud/danky
- Root directory: / در حالت خروجی از پوشه ریشه مخزن
- Build command: خالی برای پنل HTML ایستا
- Build output directory: پوشه دقیق پنل محصول، برای مثال family-guard/dashboard
- اگر Root directory را خود پوشه پنل گذاشتید، خروجی را . انتخاب کنید؛ دو روش را با هم ترکیب نکنید.

## ۶. CORS و تنظیمات

Origin دقیق هر پنل وب باید در CORS_ALLOWED_ORIGINS سرویس مربوطه ثبت شود. مقدار wildcard مجاز نیست. CORS جایگزین احراز هویت یا کنترل مجوز نیست. کلاینت بومی Android ممکن است Origin نداشته باشد؛ API باید توکن و مجوز واقعی را سمت سرور بررسی کند.

## ۷. چک‌لیست پیش از تولید

- شناسه محصول یکتا و ثبت‌شده باشد.
- سطح حساسیت و محل ذخیره داده تعیین شده باشد.
- اگر D1 اشتراکی استفاده می‌شود، جداسازی product_key و account_id در تمام queryها اجرا و آزمون شده باشد.
- اگر داده حساس یا پرحجم است، D1 اختصاصی محصول انتخاب شود.
- migration در محیط محلی یا staging اجرا و آزمون شود.
- secret در Variables & Secrets تنظیم شود، نه در Git، APK یا JavaScript سمت کاربر.
- CORS با Origin واقعی محدود شود.
- داده قدیمی/منقضی به‌عنوان داده زنده نمایش داده نشود.
- توقف/لغو/حذف و سیاست نگهداری داده تعریف شود.
- آزمون خودکار، آزمون حریم خصوصی، آزمون چندحسابی و آزمون بار متناسب با هدف اجرا شود.
